# 天赋节点搜索（P2 的第一块）

2026-11-03，分支 `agent/build-service-20261103`。只做了引擎与接口，**没有界面**。

## 命令

```lua
{ cmd = "nodes", query = "energy shield", limit = 20 }
→ { ok, query, total, nodes = [{
      id, name, type, ascendancy,
      allocated,          -- 已经点了
      weaponSet,          -- 0 = 两组都用，1 / 2 = 只属于某组（节点自己的 allocMode）
      cost,               -- 从「已点节点」出发还要点几个未点节点才能到；nil = 走不到
      stats }] }
```

排序：已点的在前，然后按 `cost`，再按名字。查询少于两个字符直接拒绝。

## 路径成本怎么算

对天赋图做**0-1 BFS**（已点的边权 0，未点的边权 1），从所有已点节点同时出发。所以：

- 已经点过的节点 `cost = 0`；
- 隔一个未点节点的 `cost = 1`；
- 与当前区域不连通（比如另一个升华、或者需要穿过未开放区域）→ `cost = nil`，不会假装 1 点可达。

这一步只解决"要走几个点"，**不判断合法性**（起点、升华、武器组专属点、必须按顺序的前置等）。按设计文档的口径，这只是"候选路径"，不是可以替玩家做决定的结论。

## 界面（2026-11-03 追加）

天赋页的搜索框现在走引擎：

- 输入时先在本地做即时匹配（不等引擎），约 0.2 秒后引擎结果替换列表；
- 结果条显示每个命中的**已点 / 還差 N 點 / 未連通**，按近似程度排序（已点优先，然后按点数）；
- 点一条结果会把画布居中到该节点并弹出它的属性提示；
- 搜索期间不符合的节点淡出（和左侧图例筛选共用一个 `keep` 规则）。

实测（caster，Sorceress 100 级）：`energy shield` → 294 个符合，列表里"消耗暴擊球的能量護盾 已点"、后面若干"還差 1 點"；点第一条后画布居中、提示框出现。

### 匹配到的节点到底给什么（2026-11-03 追加）

搜 "energy shield" 会混进四种完全不同的东西：最大护盾、护盾百分比、充能速度、充能延迟。现在每条命中都带类别标签（由节点自己的属性行判定，`src/core/passive-intent.js`），列表里显示 `max ES / ES % / recharge / delay`，充能类不会同时被算成百分比。

分类是保守的：认不出来就是空列表，不猜。

### 中文輸入（2026-11-04 追加）

天賦頁的搜尋框可以打中文：`能量護盾`、`最大能量護盾`、`移動速度`…

- 翻譯詞表（`src/core/zh-query.js`）**以 App 自帶的 zh-TW 遊戲詞典為準**，並有測試逐條驗證每個中文寫法真的出現在那份詞典裡——詞典一漂移，測試就會失敗，而不是悄悄搜不到東西。
- 長詞優先替換（`能量護盾` 先於 `護盾`，`移動速度` 不會被拆開）。
- 結果列會顯示「→ energy shield」，告訴你實際搜的是什麼；翻不出來的字會被丟掉並標註「略過：…」，而不是拿中英混雜的字串去搜、看起來像「沒有這個節點」。

實測：`能量護盾` → 294 個符合（→ energy shield）；`最大能量護盾` → 117 個符合（→ maximum energy shield）。

### 把選中的路放進草稿（2026-11-04）

路线下方有「把這條路加進草稿」：

- 引擎命令 `allocatenodes { nodes }`：按 PoB 自己导入的方式标记节点 → `BuildAllDependsAndPaths()` → 重算 → 导出 XML；
- `engine.allocatePlan(doc, ids)` 在**副本**上做，做完把页面正在用的构筑恢复原状（真机验证：155→156 点只发生在副本上，页面仍是 153 点）；
- 结果写进当前草稿（没有就新建），草稿版本 +1，**当前构筑不变**；到「構築」页试算、采用才真正生效。

实测（caster）：搜 `能量護盾` → 点「還差 1 點」的节点 → 「把這條路加進草稿」→ 提示「已加入草稿（版本 2）」；`draftState` 里 draft=2、current=1。
